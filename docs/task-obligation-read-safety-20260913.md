# Task obligation assignment repair

The production incident after 20322a40 came from `obligationInbox`: its GET projection first timed out overdue primary requests for the whole household. Fallbacks copied the expired Task due date as another response deadline. The live Tasks loader reads this inbox, increasing exposure to unintended reassignment. Production recorded one pass on Tasks 72, 81 and 90; an ongoing loop was not observed.

Inbox queries now only read. Task lists/details, notification reads and the SSE refresh path do not reconcile assignments. Overdue processing is an explicit administrator mutation at `POST /api/v1/automation/admin/obligations/reconcile`, with selected Task IDs and current revisions checked atomically. It has no timer and no caller in a GET or browser refresh. Missing/stale revisions require refresh. Child requests also require the parent revision.

Only pending requests on unfinished, unarchived Tasks can expire. Acceptance is a response, so accepted requests do not time out. Stale requests for a former primary assignee are skipped. Fixed, already-resolved subject-based and manual primary assignments remain assigned when a response expires or is declined; changing those owners requires explicit assignment editing. This does not change initial subject-based eligibility or recurrence selection.

A replacement preserves a still-future custom deadline. Otherwise it uses the existing default Task due time if that is still future. If both have expired, it receives 24 elapsed hours from the reconciliation instant. There was no configurable Task response-window duration in the previous model. Local legacy dates use the household timezone; the renewed elapsed window is stored as an explicit UTC instant. An explicitly absent deadline stays absent. Linked supervision continues its existing no-implicit-response-deadline contract.

Initial Task creation retains its existing due-linked request contract. Reconciliation captures pending requests once and does not process its newly created replacements in the same sweep. Repeating it before a new deadline/state transition produces no assignment, obligation, notification or history changes. Repeated acceptance is also a no-op. Existing audit records remain intact.

The production repair is a separate, one-time transaction limited to Tasks 72 → Eleanor, 81 → Gracelynn and 90 → Frank. It must validate identities and saved subjects, retire current fallback assignment requests, restore source assignment responsibilities while retaining subtask participants, and append repair Activity/obligation events. Pending repair requests have no response deadline; no acceptance or historical supervision is invented. It must preserve progress and all non-assignment fields/history and must not invoke supervision reconciliation. Backfill follows only after the repaired assignments pass stability checks and its own read-only preview is clean.

Adjacent legacy Meals chooser and planning-context GET reconciliation remain outside this Task assignment fix. The guarantee here covers the specified Task, obligation, notification and live-refresh reads, not every GET in the application.
