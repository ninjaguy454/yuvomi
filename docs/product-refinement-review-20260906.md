# Yuvomi product refinement review — 6 September 2026

**Status:** Refinement implemented and visually reviewed. This report covers changes since `de4be2702dee7f1cd9828f01f9ab6c7b4bd0ad04`, including the requested notification center, themes, and layout audit. No production deployment or merge was performed.

**Subsequent release gate:** [release-readiness-20260906.md](release-readiness-20260906.md) records additional privacy/upgrade fixes, fresh validation, and narrower grocery/Reader assurances. The results below remain the historical refinement-pass results.

## 1. Executive summary

Yuvomi is a capable household product with a substantial, intentional domain model. Tasks, Calendar, Household Automation, Activity Templates, Skills, Places, presence and availability, travel contexts, Kitchen, grocery runs, wall mode, and Reader mode form useful connected workflows. The review supports improving those connections and preserving the features.

The main quality gap is consistency at the boundaries: a successful Task save followed by an accessory failure, a Calendar assembled from several partially failing sources, an alternate Reader entry point, or a Meal Plan dialog with a different context from its parent page. These boundaries can make correct-looking screens incomplete, repeat an operation, or apply a different permission or context than the user expects. They deserve priority over a visual redesign.

The existing shell provides a sound base: grouped navigation, mobile primary navigation with a More menu, shared detail/edit components, theme tokens, and dedicated wall and Reader experiences. The production review confirmed a usable dark-mode Overview, Task list and details, Kitchen, Calendar Trips, and Automation settings. Density is highest in the administrative and planning surfaces. Making the active context, permission, and recovery path clearer offers more value than removing controls.

Safe fixes in this pass strengthen shared interactions, recovery, permission parity, time handling, and grocery accounting. The separately requested notification work adds SMTP channels, household shopping-list email, and durable per-user history while preserving existing providers and scopes. Existing Tasks, Meal requests, reminders, and grocery records remain authoritative; notification receipts record what was presented and delivered.

## 3. Backend and architecture issues affecting UX

| Root cause | Concrete issue and current handling |
| --- | --- |
| **Alternate mutation/access paths do not always share safeguards** | The Task status compatibility endpoint needed the same visibility check and archive lock as canonical routes (`server/routes/tasks.js:2049`). Reader needed canonical module access and write checks (`server/routes/reader.js:39`, `:247`, `:272`). Scoped API tokens could reach auth management outside the normal scoped API gates; an auth-router guard now rejects scoped tokens there (`server/auth.js:340`). These bounded parity fixes are implemented. A complete Task lifecycle consolidation remains an architectural decision. |
| **Projection code can change the meaning of stored values** | Calendar's Meal duration end was calculated using server-local time and then serialized differently from its start. UTC arithmetic now preserves household wall-time values and midnight rollover regardless of server time zone (`server/routes/planning.js:627`). This changes the projection, not the household scheduling model. |
| **Client classification is insufficient for grocery accounting** | Generic Shopping-to-Pantry import could accept a published grocery-run item when the client lacked its provenance. A second reproduced bypass used legacy Meal-to-Shopping import to create an unlinked duplicate of already-published recipe demand. Server preflights now reject linked Pantry imports and overlapping single-Meal, weekly, and Shopping date-range Meal imports before mutation, with `GROCERY_RECONCILIATION_REQUIRED`. Mixed batches fail atomically, ordinary imports without overlap remain available, and canonical reconciliation succeeds once. See `server/routes/pantry.js`, `server/services/meal-grocery-runs.js:11`, and the import routes in `server/routes/meals.js` and `server/routes/shopping.js`. |
| **Outbound delivery has trust and identity boundaries** | Notification targets now use guarded outbound HTTP; private/LAN targets require explicit `NOTIFICATION_ALLOW_PRIVATE_NETWORK=true`. Redirects retain scheme, address, and credential protections (`server/services/notification-providers/guarded-fetch.js`, `server/utils/http.js`). Shopping email resolves a household recipient by user ID and a single stored mailbox, rather than accepting an arbitrary address (`server/routes/shopping.js:842`, `server/services/member-email.js:53`). |
| **Multiple partial state models increase change risk** | Task creation, Reader, automation, recurrence, assignment, and grocery generation have different entry points. The review does not establish that their semantics should be merged automatically. Consolidation should first define common validation, permission, completion, and retry contracts, with assignment/rotation behavior held stable. |
| **Notifications need one recipient and delivery identity** | Direct sends and reminders previously had no common durable user history. Additive migration `10026` introduces per-user inbox receipts, five category preferences, and an inbox delivery ledger. Source keys reference existing reminders, obligations, comments, planning revisions, and grocery runs; these records are not replaced. Current module/entity access protects enqueue, history, unread count, individual lookup, and each outbound target. Legacy delivery receipts are imported when an unprocessed reminder crosses into the inbox, preserving successful targets and retry budgets. |

No broad schema migration, assignment-semantic change, or compatibility purge was undertaken. The explicitly authorized notification migration is an additive, module-neutral projection and delivery ledger in the existing fork migration namespace. It does not rewrite obligations, reminder cadence, assignment eligibility, or grocery accounting. Previously delivered notifications are not backfilled into invented history.

## 4. Changes implemented

### Product reliability and accessibility

- Task creation retains the returned ID before reminder/document work, so a recoverable accessory failure retries against the saved Task. Fixed invalid close-helper references and capture of an event button before asynchronous reassignment.
- Shared modals detect checkbox, radio, and multi-select edits and reversions. Keyboard focus stays within visible, enabled, non-inert controls, with a panel fallback when none exist.
- Automation form labels and hints are associated with their controls. Trip navigation opens the requested itinerary; expanding it exposes busy/expanded state and permits recovery from a failed load.
- Generic help text and success/error variants live in the shared layout stylesheet; Settings-specific reading width remains local.
- Meal Plan manager actions use its selected context. Visible guidance distinguishes trip operations from reusable definitions and Home household defaults. A synthetic Randomize run created twelve Meals only on the selected trip's three dates while preserving the underlying Home meal unchanged.
- Meals filters align, compact actions wrap, and Task detail participant/subtask controls use the available width. Shared input boundaries remain visible in all six theme/appearance combinations; the glass stylesheet no longer replaces them with decorative borders.
- Calendar distinguishes optional-layer failures from empty results, offers Retry, skips requests for disabled Task/Schedule layers, and avoids a stale retry render after navigation. Failed and successful retries restore focus only when appropriate. Meal end times retain wall-time meaning across server zones.
- Reader enforces module read/write permissions, hides inaccessible sections, preserves submitted fields after validation failure, and sends `private, no-store` on authenticated GET pages and access denials. The service worker excludes Reader pages, clears older Reader caches, respects `no-store`, and precaches required shared imports. The release gate identified an existing missing-header case on validation-error and login responses; it is documented separately.
- Task status/archive compatibility paths enforce visibility and locks. Grocery preflights cover generic Pantry import plus all three legacy Meal-to-Shopping import routes, preserving the canonical reconciliation ledger and rejecting mixed overlapping batches before any partial import.

### Additional requested notification integration

- Added an Email notification provider using existing application SMTP settings, one validated recipient per channel, readiness guidance, appropriate inactive-field behavior, escaped content, and logging that excludes notification text.
- Preserved Gotify, ntfy, webhook, household/user channel scopes, fork Meal reminder handling, and retry bookkeeping. Their HTTP requests gain shared SSRF protection with a documented deployment opt-in for private networks.
- Added Shopping list email as a snapshot of open items, sent only to an eligible household member's stored contact mailbox. The route validates membership and address server-side, reports actionable setup/empty-list errors, and rate-limits sends. It creates no public list link or access token.
- Reused shared mailbox lookup for password reset while preserving the existing guest-reset exception. Restricted scoped API tokens at the auth router; preserved session behavior and legacy full-access tokens.
- Confirmed upstream event-reminder fanout change `45f56920` is already behaviorally present. Existing fanout, personal override, assignment-removal, and recurring-event tests passed; no duplicate implementation was introduced.

These are semantic ports into this fork, rather than a release cherry-pick or a replacement of fork workflows. SMTP transport timeouts improve recovery but do not promise cancellation or exactly-once mail delivery.

The [notification technical appendix](notification-integration-20260906.md) maps upstream commits to the semantic port and records scope preservation, the delivery ledger, security boundaries, and transport limitations.

### Additional requested in-app notification center

The notification API provides per-user history, unread count, individual and all-read actions, persisted dismissal, and individual lookup for older Push links. It requires an authenticated browser session and rejects requests carrying API tokens, including mixed token/session requests. Restricted guest/worker accounts are excluded. Current Task visibility and private ICS subscription rules are reused; Meals and planning contexts retain their existing household module-access semantics. Losing source access hides its saved title and count and blocks subsequent outbound delivery. Deleted sources cannot expose stale content.

The bell uses the existing shared modal and navigation history. Read/dismiss actions persist across reloads; failed mutations remain recoverable. Task, subtask, Meal occurrence, Calendar, Trip, and Shopping destinations reuse existing query/deep-link paths. Browser QA exposed and fixed an overlay-close race: the router consumes the notification overlay directly, preventing a delayed Back action from replacing the destination.

Categories are explicit, reversible account preferences: Tasks, Meals, Calendar, Shopping, and Automation. Disabling one stops new receipts and outstanding delivery for that category; existing history stays available. It does not change another member's preferences or unrelated household channels. Read/dismiss state is receipt state and does not accept, fulfill, or delete a Task or Meal request. Dismissal also stops pending delivery. There is no additional object-specific mute engine or retrospective history backfill.

New assignment, mention, planning, and grocery notices use user-scoped channels. Existing due reminders retain their established household/user fanout. Web Push and configured delivery channels receive the same saved receipt identity; per-target receipts prevent replaying successful targets during retries. Repeated scheduler calls share one active run per database, and access, category, dismissal, and relevant obligation state are rechecked before each target. Shared-wall behavior is deliberately conservative: personal notification content stays hidden.

The following matrix describes actual source hooks, not every conceivable event in each module:

| Source and implemented trigger | Recipients and category | Identity and boundaries |
| --- | --- | --- |
| Existing due reminders: Tasks, Calendar events, Meals, subscriptions, Inventory dates/warranty, Pantry expiry | Existing reminder recipient after current source/module access; Tasks/Calendar/Meals or existing Other origins | `reminder:<id>`; existing scheduler and reminder fanout remain authoritative. Imported legacy target receipts avoid repeat sends. Cancelled/dismissed reminders stop pending retries. |
| Ordinary Task creation, effective reassignment, and spawned recurrence | Newly assigned users; Tasks | New effective assignment identity; identical assignment saves do not notify again. A newer assignment receipt suppresses an older pending send for the same Task/user while retaining both history entries. Existing source permission is mandatory. |
| Activity/workflow assignments, participant/supervisor requests, overrides and fallbacks | Current pending obligation recipient, or eligible open-claim pool; Automation for Activity/workflow sources, otherwise Tasks | `obligation:<id>:assigned`; primary/participant duplication for the same user collapses. Accepted/closed requests are history, not new response requests. |
| Meal execution duties and standalone claimable preparation work | Newly assigned responsible users or existing eligible claim pool; Tasks | Effective assignment or Task claimable identity; no changes to skills, roles, eligibility, or execution generation. |
| Successful Task claim | Creator and active supervisors, excluding the claimant; Tasks or Automation by source | Existing obligation event identity, or standalone Task claim identity. Repeat failed claims do not create another outcome notice. |

No-op saves/reconciliation reuse identities. Existing planning read authority is preserved. |

Coverage intentionally stops short of generic Calendar edit/assignment notices, every external import or compatibility Task assignment entry point, arbitrary automation administration/audit events, and a new escalation cadence. These require a defined recipient/importance policy and are deferred below; this implementation does not claim a universal event feed.

The grocery fallback review also checked alternate imports: the pre-fix probe demonstrated two shopping rows and Pantry quantity 2 from one published ingredient; the same probe now receives 409 before ingredient materialization and leaves one published shopping row. Focused tests additionally prove mixed weekly/date-range imports have no partial effects, ordinary legacy transfer remains available, and canonical reconciliation adds quantity 1 with one movement. Manual Pantry editing and leftover creation remain intentional inventory actions; these guards do not turn every same-name quantity change into a grocery reconciliation operation.

The release gate also tested the reverse order: legacy transfer while a canonical draft is unpublished, followed by canonical publication, generic Pantry import and reconciliation. That sequence still duplicates demand on both the exact baseline and the candidate. The new guard protects already-published outputs; it does not reserve draft demand or adopt earlier legacy transfers. Do not interpret the published-output tests as proof that every import order is protected. This existing lifecycle gap remains a decision item in the release-gate report.

### Additional requested Theme and Typography choices

Appearance settings now separate device appearance (System/Light/Dark) from account-level Theme (Warm/Neutral/Cool) and Typography (Default/Serif). Neutral and Default preserve the existing SPA appearance for accounts without a preference. Warm adds ivory, cream, and taupe surfaces with warm borders and shadows; Cool uses restrained slate-blue neutrals. Both reuse the existing semantic and module colors. The Serif option uses locally available fonts for prominent headings, dashboard dates/time, and Meal/Recipe titles; navigation, controls, metadata, and tables retain sans-serif text.

The new preferences apply immediately and use the existing per-user preferences store, requiring no schema migration. Failed saves restore the saved appearance; revision checks prevent an old request from restoring another account's colors after logout. Prepaint storage access is guarded, and session teardown clears the personal appearance cache. Reader receives account colors and heading choice server-side without JavaScript, while deliberately retaining a light e-paper surface. Wall mode's night appearance remains independent of color temperature.

Contrast checks cover all six color/appearance combinations. Small shared token corrections raise the existing light warning, dark error, and dark Records/Health accents above 4.5:1 on their reading surfaces while preserving their recognizable hues. Actual shared inputs use a separate control-border token meeting 3:1 against both control surfaces; browser QA found and corrected a later glass-style override, while decorative card borders remain unchanged. The module stylesheet audit found no page-level neutral hex colors needing replacement: the remaining literals are deliberate print colors, photo-screensaver contrast, and the white QR-code backing. They were preserved.

The completed visual matrix is in [visual-qa-20260906.md](visual-qa-20260906.md). It distinguishes desktop, tablet and mobile module coverage, all six Appearance comparisons, populated/empty states, and deliberate wall/Reader behavior from combinations not tested. Mobile Task detail controls now use available row width; actual screenshots confirmed the participant selector and one-line Add subtask control.

The design direction follows the user's color-temperature principle from the [referenced UX Planet article](https://uxplanet.org/color-decision-premium-ui-design-d6890efe11ba). Its accessible introduction was reviewed; the member-only remainder was not accessible. Implementation follows the user's explicit palette and typography requirements.

## 6. Deferred recommendations

- **Defer:** an absolute notification delivery deadline, SMTP cancellation, and exactly-once guarantees. A remote server can accept mail before the client sees failure; changing retry policy needs a stated delivery contract.
- **Needs architectural decision; deferred to a dedicated follow-up:** define a timezone/storage contract across recurrence, travel, wall displays, DST, and household/server/browser zones. This pass fixes the proven Calendar Meal-duration projection and aligns Randomize trip bounds with the existing backend contract; it does not reinterpret persisted household times.
- **Defer pending product decision:** generic Calendar changes, assignment imports/compatibility entry points, administrative automation events, and new notification escalation/reminder cadence. Define recipients, importance, and grouping before expanding the implemented source matrix. Existing obligations, reminders, and audit history remain authoritative.
- **Defer:** notification retention/archiving and arbitrary source/object-specific mute controls. The implemented named category preferences are explicit and reversible; a larger policy engine would add behavior beyond this bounded scope.
- **Defer:** per-device Web Push retry receipts. The existing sender reports zero when no device accepts a delivery, including some transient failures; the current aggregate target is then skipped. The durable inbox remains available, but Push is not a guaranteed delivery channel.
- **Defer:** N+1/query consolidation and broad performance work until representative request counts, slow queries, household size, and mobile timings are measured. Avoid speculative batching that changes filtering or assignment behavior.
- **Defer:** a broad language/localization pass, Reader locale/week-start expansion, and optional browser-storage wrappers. Apply targeted copy fixes now; use a separate pass with translation and restricted-storage tests for the wider surface.
- **Defer:** broad schema migrations, removal of compatibility code, and large service rewrites. Require usage evidence and a migration/rollback plan first.
- **Defer:** wholesale information-architecture or visual redesign. Validate context cues, progressive disclosure, and real household workflows before rearranging working modules.

## 8. Remaining risks
